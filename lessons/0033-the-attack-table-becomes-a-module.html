The Attack Table Becomes a Module

Your first real refactor. The combat math has been living inside the player — we lift it out into one cited, reusable file, and the game plays exactly the same.

TODAY

Press F5 after the change and combat is identical — same misses, same crits, same rage. But the seven researched formulas now live in one file, combat_table.gd, that knows nothing about the player. That file is what Lesson 34 will test.

Why touch working code at all?

Right now player.gd does two very different jobs. It runs the player — input, animation, the sword, the camera. And it also is the rulebook of WoW combat: miss chance, dodge, parry, glancing, crit, rage. Those formulas are the most important numbers in the game, and they're buried 200 lines deep in a script about walking around.

◇ a module is code that does one job and hides the rest

When a chunk of logic (1) is about one thing, (2) can be described without mentioning the code around it, and (3) you'd want to reuse or test on its own — that's a module waiting to be born. The attack table is all three: it's pure arithmetic on two levels, the wolf will want it too, and we want to prove it matches Vanilla without launching the game.

The tool: class_name + static func

class_name

Put class_name CombatTable at the top of a script and Godot registers that name everywhere — any other script can write CombatTable.miss_chance(...) with no preload, no node, no instance. It becomes a word in the language.

static func

A static function belongs to the class, not to an object. It can't touch self or any node — only its arguments. That restriction is the point: it forces the function to be pure (same inputs → same output, no side effects), which is exactly what makes it testable.

Part A — create the module

In the FileSystem dock, right-click res:// → Create New → Script…, name it combat_table.gd. Replace its contents with this. Notice: no extends a node, no _ready — just named numbers.

GDScript · combat_table.gd
class_name CombatTable
# The Vanilla-1.12 attack table, in one place. Every white swing is one d100 roll
# walked through bands: Miss -> Dodge -> Parry -> Glancing -> Crit -> Hit.
# These functions are PURE: numbers in, numbers out, no node state. That is what
# lets us test them headless (Lesson 34). Every formula cites wow-combat-values.md.

const BASE_CRIT := 5.0          # §5: ~5% innate melee crit
const CRIT_MULTIPLIER := 2.0    # §5: crits deal 200%

# Δ = (targetLevel − attackerLevel) × 5.  §2 — drives miss & glancing.
static func skill_delta(attacker_level: int, target_level: int) -> int:
    return (target_level - attacker_level) * 5

# §3: miss% = 5 + Δ×0.1 (exact for targets within 2 levels — every fight we have).
static func miss_chance(attacker_level: int, target_level: int) -> float:
    return 5.0 + skill_delta(attacker_level, target_level) * 0.1

# §4: 5% + 0.5%/level above.
static func dodge_chance(attacker_level: int, target_level: int) -> float:
    var gap := maxi(target_level - attacker_level, 0)
    return 5.0 + gap * 0.5

# §4: 5% base, +3%/level above (+3 = 14%). Front only.
static func parry_chance(attacker_level: int, target_level: int) -> float:
    var gap := maxi(target_level - attacker_level, 0)
    return 5.0 + gap * 3.0

# §6: 0% vs equal/lower; +10%/level above (only when YOU hit up).
static func glancing_chance(attacker_level: int, target_level: int) -> float:
    var gap := target_level - attacker_level
    if gap <= 0:
        return 0.0
    return 10.0 + gap * 10.0

# §5: base crit − 1%/level above (suppression), floored at 0.
static func crit_chance(attacker_level: int, target_level: int, base_crit := BASE_CRIT) -> float:
    return max(base_crit - (target_level - attacker_level), 0.0)

# §6: glancing damage band [low, high]. At +3 (Δ=15) → ~0.55..0.75 of normal.
static func glancing_band(attacker_level: int, target_level: int) -> Vector2:
    var skill_diff := skill_delta(attacker_level, target_level)
    var low := clampf(1.3 - 0.05 * skill_diff, 0.01, 0.91)
    var high := clampf(1.2 - 0.03 * skill_diff, 0.2, 0.99)
    return Vector2(low, high)

static func glancing_damage(attack_damage: float, attacker_level: int, target_level: int) -> float:
    var band := glancing_band(attacker_level, target_level)
    return attack_damage * randf_range(band.x, band.y)

# --- Rage (§8). C grows with level: L1 ≈ 7.5, L60 ≈ 230.6. ---
static func conversion_value(level: int) -> float:
    return 0.0091107836 * level * level + 3.225598133 * level + 4.2652911

static func rage_from_dealing(damage: float, weapon_speed: float, is_crit: bool, level: int) -> float:
    var f := 7.0 if is_crit else 3.5
    return 7.5 * damage / conversion_value(level) + f * weapon_speed / 2.0

static func rage_from_taking(damage: float, level: int) -> float:
    return 2.5 * damage / conversion_value(level)
⚠ maxi, not max

We use maxi() (integer max) instead of plain max() in dodge_chance/parry_chance. With the typed := assignment, max() returns a Variant — and this project treats that warning as an error. maxi() returns a real int, so the type is clean. (This is a genuine error you'll hit; it's why it's called out.)

Part B — rewire the player to call the table

Now player.gd stops owning the math and starts asking for it. In attack(), replace the five local calls:

GDScript · player.gd — inside attack()
    var roll = randf() * 100.0
    var miss = CombatTable.miss_chance(level, t.level)
    var dodge = CombatTable.dodge_chance(level, t.level)
    var parry = CombatTable.parry_chance(level, t.level)
    var glancing = CombatTable.glancing_chance(level, t.level)
    var crit = CombatTable.crit_chance(level, t.level, base_crit)

…and the glancing-damage line, a few lines down:

GDScript · player.gd
        var dmg = roundi(CombatTable.glancing_damage(attack_damage, level, t.level))

Then the two rage helpers shrink to one line each, and conversion_value() and all six *_chance functions are deleted from player.gd — they live in the module now:

GDScript · player.gd
func gain_rage_dealing(damage, is_crit):
    add_rage(CombatTable.rage_from_dealing(damage, weapon_speed, is_crit, level))

func gain_rage_taking(damage):
    add_rage(CombatTable.rage_from_taking(damage, level))
CombatTable.miss_chance(level, t.level) — no preload, no instance. The class_name made CombatTable a global word. level is the player's; t.level is the target wolf's.
add_rage(...) stays in the player — it touches the rage bar (a node). Only the pure arithmetic moved out. That line — node state stays, math leaves — is the whole judgement call of a refactor.

The idea that proves it worked: the deletion test

◈ "could I delete this and explain what broke?"

A good module passes the deletion test: if you deleted combat_table.gd, you could say in one breath what stops working (every swing's outcome) and nothing else would be mysteriously entangled. The combat math used to fail that test — deleting those lines from player.gd would have taken movement and animation context with them. Now it's a clean seam.

Do it & verify

1

Create combat_table.gd (Part A) and rewire player.gd (Part B). Delete the old crit_chance/dodge_chance/parry_chance/miss_chance/glancing_chance/glancing_damage and conversion_value functions from player.gd.

2

Press F5. Fight a wolf. Nothing should look different — misses miss, crits flash, rage fills. That sameness is the win: a refactor changes the code's shape, never its behaviour.

3

Tune one number: open combat_table.gd, change BASE_CRIT to 50.0, run, and watch crits everywhere. Set it back to 5.0. One file, one source of truth.
