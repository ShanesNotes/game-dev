Combat FX, One Home

Damage numbers, miss words, sparks, and blood all do the same job: spawn a tiny feedback node and let it clean itself up. Today they stop living in two different actors.

TODAY

Player, wolf, and sword pickup all ask one autoload for combat feedback. The game looks the same, but the duplicate spawners disappear: one CombatFX bus owns floating text and particle bursts.

The smell: feedback code copied into actors

The player has combat decisions to make. The wolf has AI and death to manage. Neither one should also remember how to construct a floating label, which texture a spark uses, or which gravity value makes blood fall. Before this lesson, that construction lived in both scripts:

old shape · scattered helpers
player.gd: spawn_text_over(), spawn_number(), spawn_sparks()
wolf.gd:   spawn_number(), spawn_blood()
sword.gd:  body.spawn_sparks(...)
⚠ duplicate helpers are soft coupling

None of those helpers are huge. That's why the smell is easy to ignore. But every copy assumes where to add the node, which scene to preload, and which magic numbers make the effect feel right. Change the damage-number scene once, and you have to remember every little factory that stamps it out.

The move: one tiny autoload, like Sfx

Lesson 27 already gave sound one global home: Sfx.play("hit"). Combat feedback is the visual twin of that idea. CombatFX is not an event bus for game rules; it is a little workshop that builds short-lived visual effects.

autoload

A script Godot creates once at startup and exposes by name. Use it for small global services like Sfx and now CombatFX.

factory

A function whose job is to build a node correctly. Callers ask for the result; they do not know the construction recipe.

effects layer

The scene marks World with the "effects_layer" group. CombatFX spawns world-space feedback there, then falls back to current_scene only for tests or tiny scenes.

Part A — register the bus

Create res://combat_fx.gd, then register it in Project Settings → Autoload as CombatFX. The project file ends up with:

project.godot
[autoload]

Sfx="*res://sfx.gd"
CombatFX="*res://combat_fx.gd"

The order is boring on purpose: sound and visual feedback are siblings. Actors request them; the buses own the messy lifetime details.

Part B — move the construction recipes

GDScript · combat_fx.gd
extends Node

const DAMAGE_NUMBER = preload("res://damage_number.tscn")
const SPARK = preload("res://assets/spark.png")
const BLOOD = preload("res://assets/soft_dot.png")
const EFFECTS_LAYER_GROUP = &"effects_layer"

func text_over(target, words: String, color: Color, font_size: int = 18):
    if not is_instance_valid(target):
        return null
    return text_at(target.global_position + Vector2(-8, -30), words, color, font_size)

func damage_number(target, amount: int, color: Color, font_size: int = 18):
    return text_over(target, str(amount), color, font_size)

func text_at(at: Vector2, words: String, color: Color, font_size: int = 18):
    var n = DAMAGE_NUMBER.instantiate()
    _effects_root().add_child(n)
    n.global_position = at
    n.show_text(words, color, font_size)
    return n
text_over(target, ...) — caller speaks in game terms. Player says "put Miss over that wolf"; the bus decides the pixel offset and scene instantiation.
damage_number(...) — number is just text with a convention. The old setup(amount, color) wrapper still exists on the label, but the bus routes both words and numbers through the same path.
return n — test seam. Gameplay ignores the return value, but the headless test can inspect the node and prove the factory built the right kind of thing.

The two particle recipes share one private helper:

GDScript · combat_fx.gd — bursts
func sparks(at: Vector2, color: Color, count: int):
    return _particle_burst(SPARK, at + Vector2(0, -10), color, count,
        0.35, 40.0, 90.0, Vector2(0, 160), 0.5, 1.0)

func blood(at: Vector2):
    return _particle_burst(BLOOD, at + Vector2(0, -8), Color(0.72, 0.13, 0.1), 6,
        0.4, 25.0, 60.0, Vector2(0, 220), 0.3, 0.6)

func _particle_burst(texture, at: Vector2, color: Color, count: int, lifetime: float,
        velocity_min: float, velocity_max: float, gravity: Vector2,
        scale_min: float, scale_max: float):
    var p = CPUParticles2D.new()
    p.texture = texture
    p.amount = count
    p.one_shot = true
    p.explosiveness = 1.0
    p.lifetime = lifetime
    p.initial_velocity_min = velocity_min
    p.initial_velocity_max = velocity_max
    p.gravity = gravity
    p.scale_amount_min = scale_min
    p.scale_amount_max = scale_max
    p.color = color
    p.z_index = 30
    _effects_root().add_child(p)
    p.global_position = at
    p.emitting = true
    p.finished.connect(p.queue_free)
    return p

func _effects_root():
    var layer = get_tree().get_first_node_in_group(EFFECTS_LAYER_GROUP)
    if layer != null:
        return layer
    if get_tree().current_scene != null:
        return get_tree().current_scene
    return get_tree().root
◈ why not make a giant VFX system?

Because the game does not need one yet. This is one shallow, useful module: three public verbs (text_over, damage_number, sparks/blood) and one private recipe. No pooling, no plugin, no new dependency. Depth without ceremony.

Part C — actors ask; actors stop building

Now the player only describes the feedback it wants:

DELETION TEST

Delete spawn_text_over, both spawn_number helpers, spawn_sparks, and spawn_blood. If the game still boots and the CombatFX test passes, the duplication really moved — it was not copied again under a new name.

Part D — test the helper

A --script test does not rely on the autoload's global name at compile time, so it preloads combat_fx.gd, adds an instance to the test tree, and calls the same public functions.

terminal
godot --headless --path projects/first-steps --script res://tests/test_combat_fx.gd

Expected ending:

expected output
  ok   blood amount = 6
  ok   blood offset = (30.0, 32.0)
PASS — CombatFX builds shared text and particle effects
Why test visual code at all? Not to judge prettiness — a screenshot verdict can do that later. This test checks the factories: correct node type, correct text, correct font size, one-shot particles, and the offsets we depend on.
Why keep the boot check? The test proves the helper and its effects-layer target. The boot proves the project autoload name is registered and real gameplay scripts compile against CombatFX.
