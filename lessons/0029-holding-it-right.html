Holding It Right: The Directional Sword

Lesson 17 bolted the sword to one side of the body — fine, until Will turns around and the blade floats on the wrong side like a sticker. Today the sword follows his hands: right hand facing right and down, mirrored to the left hand facing left, tucked behind his back facing away.

The big idea: a sprite is a flat lie

A 3D game rotates a sword model and it just works. A top-down 2D character is four flat drawings pretending to be one person — so "holding a sword" is also four flat lies, and you fake each one with three cheap tools: where the sword sprite sits (position), which way it's drawn (flip_h), and whether it draws in front of or behind the body (show_behind_parent). Get those right per facing and nobody ever notices. Get one wrong and everybody does.

flip_h

Mirrors a sprite horizontally — for free, no second drawing. One blade drawn for the right hand becomes the left-hand blade with flip_h = true. (The wolf has used this since Lesson 9 to face its prey.)

show_behind_parent

A CanvasItem switch: "draw me in the behind group." Godot draws a node's behind-flagged children first, then the node's own drawing, then its other children — so the Sword (a child of the Player, sibling of the AnimatedSprite2D body) jumps from after the body sprite to before it. It stays attached and moves with the Player; only its slot in the Player's draw order changes.

match

GDScript's many-way branch. match facing: with one block per value reads like a table — much cleaner than four chained elifs when every case does the same kind of thing.

baked rotation

Rotating art in the generator (once, on real pixels) instead of rotating the node at runtime (every frame, off the pixel grid). The result ships as a normal sprite.

Part A — the rest pose moved into the pixels

In Lesson 17 the sword rested at an angle by rotating the node: SWORD_REST_DEGREES = 25.0. The overhaul changed that constant to zero — and the sword still rests at 25°. The angle moved into the art: the asset pipeline (assets/gen_polish.py) rotates the clean sword sprite once, with nearest-neighbor sampling, and saves it as sword_held.png. The scene's Sword sprite now uses that texture:

GDScript · player.gd
const SWORD_REST_DEGREES = 0.0   # 25-degree rest pose is baked into sword_held.png
Python · assets/gen_polish.py
def make_sword_held():
    im = Image.open('sword_clean.png').convert('RGBA')
    rot = im.rotate(-25, resample=Image.NEAREST, expand=False)
    rot.save('sword_held.png')
◈ WHY BAKE? PIXELS LIVE ON A GRID

Rotate a pixel-art sprite at runtime and its texels land between screen pixels — some render fat and others thin, off the chunky grid every other drawing lives on. (Our snap_2d_transforms_to_pixel project setting keeps a fixed rotation from shimmering as you walk — but the uneven texels remain, frozen wrong. And the moment the angle animates, like our swing, the edges crawl.) Rotate it once in the generator and the result is re-snapped to the texture grid like any other drawing: chunky and stable forever. Rule of thumb: rotation that never changes belongs in the art; rotation that animates belongs in code — unless you can afford a baked frame per step. As of today the swing still rotates live (watch the blade mid-arc with educated eyes and you can see it); baking it too is the next lesson's whole story.

Part B — one function owns the pose

Every facing gets a hand position, a mirror flag, and a front/behind decision — one match, called whenever facing changes:

GDScript · player.gd
# The held sword follows the hand: right side when facing right/down,
# mirrored to the left hand when facing left, tucked behind the body
# when facing away.
func update_sword_pose():
    if not has_sword:
        return
    match facing:
        "right":
            sword.position = Vector2(10, 2)
            sword.flip_h = false
            sword.show_behind_parent = false
        "left":
            sword.position = Vector2(-10, 2)
            sword.flip_h = true
            sword.show_behind_parent = false
        "down":
            sword.position = Vector2(9, 3)
            sword.flip_h = false
            sword.show_behind_parent = false
        "up":
            sword.position = Vector2(-9, 0)
            sword.flip_h = true
            sword.show_behind_parent = true
The early return — before the pickup, there's no pose to manage. Guard clauses first; the function body assumes a sword exists.
The numbers are hand anchors. (10, 2) is "the right fist, mid-body" in the character's local pixels. They were found the honest way: nudge, run, squint, repeat. Pose code is tuned, not derived.
"up" gets both tricks: mirrored and behind. Facing away, you see Will's back — his right hand is now on screen-left, and his body should hide most of the blade. Two booleans sell the entire 180° turn.

Part C — call it when facing changes

Three call sites. The first two you've already met:

GDScript · player.gd
func equip_sword():
    has_sword = true
    sword.visible = true
    sword.rotation_degrees = SWORD_REST_DEGREES
    update_sword_pose()

update_animation() (Lesson 7's walk logic) already sets facing from input — it now ends with an update_sword_pose() call, so walking keeps the blade in the correct hand. The third call site is new, and it's the one that makes combat look intentional — turning to face your victim:

GDScript · player.gd
# Turn the standing pose toward a point (movement animation wins while walking).
func face_toward(point: Vector2):
    var d = point - global_position
    if abs(d.x) > abs(d.y):
        facing = "right" if d.x > 0 else "left"
    else:
        facing = "down" if d.y > 0 else "up"
    if velocity == Vector2.ZERO:
        anim.animation = "walk_" + facing
        anim.stop()
        anim.frame = 0
    update_sword_pose()
Dominant axis wins. abs(d.x) > abs(d.y) picks the facing that best points at the target — the same idea Lesson 7 used to pick a walk row from input, now reused for aim.
anim.frame = 0 — settle on the standing pose. Without it, turning while idle freezes Will mid-stride on whatever frame the last walk left behind. Frame 0 of each walk row doubles as that row's "standing" drawing.
The velocity guard keeps priorities straight: if Will is walking, the walk animation owns the body; face_toward() only repaints the standing pose. The sword pose updates either way — the hand must be right even mid-stride.

The player's swing() opens with face_toward(target.global_position) — that's why Will turns before every hit instead of slashing the air behind him.

Part D — the mirror debt

One honest wrinkle before we close: the swing (Lesson 17's live rotation tween) doesn't know about any of this yet. A mirrored sprite rotated by the same angle swings backwards — so at today's checkpoint, attack while facing left and watch closely: the blade sweeps the wrong way. A quick patch exists (var swing_to = 65 if sword.flip_h else -65 — mirror the angle whenever the art is mirrored), but we're not taking it.

Next lesson the swing stops rotating live entirely — it becomes a sequence of pre-rotated textures, and since flip_h mirrors whatever texture is showing, the same flag that moves the blade into the left hand will mirror every frame of the arc. The correct left-handed swing will cost zero extra code. Good representation choices don't just fix bugs — they delete the code that would have fixed them.

FEEL IT YOURSELF — BREAK ONE CASE

In update_sword_pose(), set the "up" branch's show_behind_parent to false, run, and walk north: the blade floats over Will's back like a magnet. Now change the "right" position to Vector2(16, 2): the sword detaches from his fist entirely. Revert both. You now know exactly what each lie is doing.
