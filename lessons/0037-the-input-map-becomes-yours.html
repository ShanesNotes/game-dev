Why this lesson exists

Early lessons were allowed to use ui_left, ui_right, ui_up, and ui_down because they need no setup. That's the right first five minutes. But ui_* belongs to Godot's UI navigation vocabulary: menu focus, buttons, sliders, dialog boxes. A game eventually deserves names that describe game intent.

◈ action names should be verbs, not devices

move_left means "the player wants to move left." It can be A, Left Arrow, D-pad Left, or a stick tilted left. The code never asks which device did it — it asks whether the verb is active.

The final map

Open Project → Project Settings… → Input Map. These are the custom actions the project now uses:

move_left

A, Left Arrow, left stick X−, D-pad Left.

move_right

D, Right Arrow, left stick X+, D-pad Right.

move_up

W, Up Arrow, left stick Y−, D-pad Up.

move_down

S, Down Arrow, left stick Y+, D-pad Down.

target_next

Tab or right shoulder / RB. Cycles to the nearest wolf you are not already targeting.

attack

Space, right mouse button, or gamepad bottom face button (A / Cross).

⚠ why right mouse, not left?

Lesson 15 could get away with a simple attack binding before click-targeting existed. Once Lesson 19 gives left click to wolf selection, attack's mouse binding moves to the right mouse button. The action name stays attack; only the event list changes.

Movement code does not get more complicated

The whole movement swap is just named actions inside the same Input.get_vector call. The final code keeps those names as StringName constants so hot-path reads do not allocate new strings:

GDScript · player.gd — final movement read
const ACTION_MOVE_LEFT: StringName = &"move_left"
const ACTION_MOVE_RIGHT: StringName = &"move_right"
const ACTION_MOVE_UP: StringName = &"move_up"
const ACTION_MOVE_DOWN: StringName = &"move_down"

var direction: Vector2 = Input.get_vector(ACTION_MOVE_LEFT, ACTION_MOVE_RIGHT, ACTION_MOVE_UP, ACTION_MOVE_DOWN)
velocity = direction * speed
move_and_slide()
Same order as Lesson 3: left, right, up, down. Negative X, positive X, negative Y, positive Y.
More devices, no more branches: keyboard, D-pad, and analog stick all flow through the same vector. Diagonals still normalize; stick deadzones still apply.

Discrete actions: target and attack

Movement is continuous, so it is read every physics frame. Targeting and attacking are one-shot verbs, so the player receives them in _unhandled_input after UI has had a chance to consume the event:

GDScript · player.gd — final discrete reads
const ACTION_TARGET_NEXT: StringName = &"target_next"
const ACTION_ATTACK: StringName = &"attack"

func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed(ACTION_TARGET_NEXT):
        target_nearest_wolf()
        get_viewport().set_input_as_handled()
    elif event.is_action_pressed(ACTION_ATTACK):
        start_auto_attack()
        get_viewport().set_input_as_handled()
target_next — Tab/RB as a targeting verb. The function chooses the nearest wolf you are not already targeting. Mouse targeting still works through the wolf's click handler; the Input Map adds a keyboard/controller route.
attack — one action, many devices. Space, right mouse, and A/Cross all call the same code. When the sword is missing, the same action triggers the "Find the sword" feedback.
_unhandled_input — gameplay after UI. A pause menu or button can consume a click before the player script sees it; once the player handles a targeting or attack event, it marks the event handled.
