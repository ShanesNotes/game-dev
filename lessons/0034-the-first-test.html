Why a test, and why now?

Lesson 33 made CombatTable pure — numbers in, numbers out, no nodes. That wasn't just tidiness: pure functions are the only kind you can check without running the game. You don't need a wolf, a swing timer, or a window. You just call CombatTable.miss_chance(1, 2) and ask: is it 5.5, like the reference says?

◇ a test is a second opinion that never gets tired

Your reference/wow-combat-values.md is the source of truth for every combat number. A test is just code that re-reads that truth and checks the game still agrees. Write it once; it guards those values forever — every time you run it, for free.

The tool: a headless SceneTree script

Godot can run a single script with no window, no main scene — perfect for a test. A script that extends SceneTree gets a _init() that fires the moment Godot boots; we do our checks there and call quit(0) for success or quit(1) for failure. (The exit code is how a CI server, later, will know pass from fail.)

Write the test

Create a folder res://tests/, and inside it a script test_combat_table.gd:

GDScript · tests/test_combat_table.gd
extends SceneTree
# Runs headless, game closed. Asserts CombatTable against the cited numbers in
# reference/wow-combat-values.md. We preload the module rather than rely on the
# global class_name, so the test runs even before the editor refreshes its cache.

const CT = preload("res://combat_table.gd")

var _fails := 0

func _init() -> void:
    # Player is L1; vary the target's level to walk the Δ table.
    expect("miss same-level", CT.miss_chance(1, 1), 5.0)
    expect("miss +1 (Δ=5)",   CT.miss_chance(1, 2), 5.5)
    expect("miss +2 (Δ=10)",  CT.miss_chance(1, 3), 6.0)
    expect("dodge same-level", CT.dodge_chance(1, 1), 5.0)
    expect("dodge +3",         CT.dodge_chance(1, 4), 6.5)
    expect("parry +3",         CT.parry_chance(1, 4), 14.0)
    expect("glancing +1",      CT.glancing_chance(1, 2), 20.0)
    expect("glancing +3",      CT.glancing_chance(1, 4), 40.0)
    expect("crit same-level",  CT.crit_chance(1, 1), 5.0)
    expect("crit +1",          CT.crit_chance(1, 2), 4.0)
    expect("conversion L1",    CT.conversion_value(1), 7.5, 0.05)
    expect("conversion L60",   CT.conversion_value(60), 230.6, 0.1)

    if _fails == 0:
        print("PASS — all combat-table values match wow-combat-values.md")
        quit(0)
    else:
        printerr("%d FAILURE(S)" % _fails)
        quit(1)

func expect(label: String, got: float, want: float, tol := 0.001) -> void:
    if abs(got - want) <= tol:
        print("  ok   " + label)
    else:
        _fails += 1
        printerr("  FAIL " + label + "  got %s want %s" % [got, want])
const CT = preload("res://combat_table.gd") — we load the file directly rather than use the global CombatTable name. A headless run may not have refreshed the class registry yet; preload sidesteps that entirely.
expect(label, got, want, tol) — one tiny assert helper. Floats are never exactly equal, so we compare within a tolerance. A real value (rage's C) gets a looser tol; the band percentages are exact.
quit(0) / quit(1) — the verdict, as an exit code. 0 = all good; 1 = something drifted. Humans read the words; machines read the number.

Run it

In the terminal (left), from the repo root:

terminal
godot --headless --path projects/first-steps --script res://tests/test_combat_table.gd
--headless

No window, no rendering. Just the engine, running your script. Fast enough to run on every save.

--path

Which project to load (so res:// resolves). Points at projects/first-steps.

--script

Run this one script and nothing else — no main scene. The SceneTree script takes over.

You should see a column of ok lines and then:

expected output
  ok   miss same-level
  ok   miss +1 (Δ=5)
  …
PASS — all combat-table values match wow-combat-values.md

See it catch a bug

1

Open combat_table.gd and sabotage one value — change miss's 5.0 to 4.0. Run the test again.

2

It goes red: FAIL miss same-level got 4.0 want 5.0, then 1 FAILURE(S). The test caught a value drifting from the reference — exactly its job.

3

Put it back to 5.0. Green again. That loop — change, run, see green — is how every serious codebase stays correct while it grows.
