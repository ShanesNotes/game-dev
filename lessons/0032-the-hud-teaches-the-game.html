The HUD Teaches the Game

Three hint chips sit at the bottom of the screen: move, target, attack. Nobody reads manuals, and nobody should have to — so each chip watches for its own action, dims the moment Will performs it, and when all three are proven learned, the whole strip excuses itself.

TODAY

Start the game: a quiet bar lists the three verbs. Walk — the Move chip dims. Pick a wolf — Target dims. Throw your first swing — Attack dims, and two seconds later the strip fades out for good. A brand-new player was taught the whole game without a single popup, pause, or "OK" button.

The big idea: the reactive tutorial

Most tutorials interrupt: freeze the game, show a box, demand a click. Ours observes: show the available verbs, keep the game fully playable, and treat the player's own actions as proof of learning — retiring each hint the moment its job is done. The player never finishes a tutorial; it simply stops being there. The best tutorial is one nobody notices completing. The machinery is one dictionary, two functions, and the polling loop the HUD already runs.

dictionary as a set

_hints_done stores {"move": true} — but nothing ever reads the true. What matters is whether the key exists (.has()). A dictionary used this way is a checklist: present = done.

@onready dictionary

@onready works on any expression — including a dictionary of nodes. One lookup table from hint name to Label replaces three separate variables and lets _complete_hint() take a string instead of a node.

evidence probe

A per-frame question whose "yes" proves the player did something: an input vector, a target's validity, a running timer. Each hint owns one probe — and they're three different kinds of evidence.

Part A — the strip

The scene side is one dark bar pinned to the bottom of the HUD with three labels on it (per the draw-order rule from Lesson 31, it sits below the wince layer but above DeathScreen in the tree — so it draws over the flash and under the death fade):

Part B — the checklist and the probes

In hud.gd, the handles and the checklist:

GDScript · hud.gd — with the other @onready vars
@onready var hint_strip = $HintStrip
@onready var hints = {
    "move": $HintStrip/HintMove,
    "target": $HintStrip/HintTarget,
    "attack": $HintStrip/HintAttack,
}

var _hints_done = {}

The probes run from the same _process() you saw in Lesson 31 — the call marked "next lesson's star" is today's star:

GDScript · hud.gd
func _update_hints(player):
    if not _hints_done.has("move") and Input.get_vector("move_left", "move_right", "move_up", "move_down") != Vector2.ZERO:
        _complete_hint("move")
    if not _hints_done.has("target") and is_instance_valid(player.target):
        _complete_hint("target")
    if not _hints_done.has("attack") and player.has_sword and not player.swing_timer.is_stopped():
        _complete_hint("attack")
Three kinds of evidence. Move asks the input directly (the same Input.get_vector from Lesson 3). Target asks game state — a valid target exists, no matter whether Tab, RB, or a click set it. Attack asks for compound proof: a sword in hand AND the swing timer actually running — mashing the attack key empty-handed proves nothing, so it completes nothing.
Honest fine print: game-state evidence proves an action happened — not that the player chose it. Lesson 31's take_damage retaliates (it targets the attacker and starts the swing timer), so a wolf that bites Will can dim Target — and, once the sword is in hand, Attack — before he ever presses Tab or Space. We accept the false positive: by that point Will is targeting and swinging on screen, which is the thing the chip existed to show.
The has() guard makes each probe one-shot: once a key is in the checklist, that probe is never evaluated again. Cheap, and it means _complete_hint() can never fire twice for one chip — the same exactly-once thinking as Lesson 31's latch, in dictionary form.

Part C — dim, don't delete

GDScript · hud.gd
func _complete_hint(key):
    _hints_done[key] = true
    var t = create_tween()
    t.tween_property(hints[key], "modulate:a", 0.3, 0.5)
    if _hints_done.size() == hints.size():
        var f = create_tween()
        f.tween_interval(2.0)
        f.tween_property(hint_strip, "modulate:a", 0.0, 1.2)
0.3, not 0. A dimmed chip is a receipt: "learned, but still here if you blank on the key." Deleting a hint the instant it's used punishes exactly the player who needs it back. The dim is the reward signal; removal waits for the full set.
The graduation: when the checklist matches the chip table (size() == size()), a second tween waits two beats and fades the whole strip — interval-then-fade, the toast rhythm from Lesson 28. Fading hint_strip takes the three labels with it: children inherit their parent's modulate.
Same ledger entry: these probes ride the HUD's polling _process(), the debt Lesson 31 put on the books (events-over-polling, The Forge). One refactor will pay for all three tenants.
FEEL IT YOURSELF — BREAK THE KINDNESS

Set the dim to 0.0 and play fresh: chips vanish the instant you use them — efficient, and weirdly punishing when you forget the targeting key ten seconds later. Put it back, then set the graduation interval to 0.0: the strip starts dying the moment the last chip dims, and the "you've learned everything" beat never lands. Tutorials have feel, too. Revert both.
